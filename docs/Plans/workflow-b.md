# Workflow B — matching with decomp-permuter

One source worker reconstructs the function, feeds a near-match to the local `decomp-permuter`, inspects its best changes and gives it a revised seed. Repeat this loop while the target has a code-generation mismatch. Start from a preserved candidate when there is one. Use m2c and the retail disassembly when starting from scratch. The worker owns the C throughout and the integrator verifies the complete wave. [Matching examples](../research/how-matching-works-20261117.md) · [Private workbench](../MATCHING_WORKBENCH.md)

## Run with one source worker

1. **Reproduce the seed.** Run the selected workbench launcher’s `watch` on the complete authored source. Identify the first instruction that matters and keep the best source, report, and any useful competing controls. Check function extent, calls, frame, relocation operands and owned data. Resolve a missing body, wrong prototype or missing side effect in C before searching for instruction order.
2. **Give the permuter a real target.** In the worker’s private root, prepare the complete retail text for scoring, the seed C and the compilation command for the selected KMC toolchain. Include executable continuation rows. Compare the unmodified seed through both compiler paths. Check that the scorer disassembles the full expected instruction stream and can see a known difference. The historical GNU 2.6 objdump produced a false zero by decoding no instructions. The reviewed trial used GNU 2.39 for scoring. Its original address map and single-row adapter were specific to its cases. [Tool and scoring review](task-logs/combat-guided-permuter-review-r1.md)
3. **Run the actual search.** Use the retained upstream `permuter.py` on the target case. Give it source choices that could explain the observed mismatch. For example, let it enumerate independent declaration orders or combinations of equivalent expressions and temporary lifetimes. Choose a search region where changing evaluation order preserves the required accesses. Keep the parent intact. Count native compilation jobs across the permuter and any simultaneous workbench check within the assigned budget. While it searches, inspect the assembly or prepare the next hypothesis.
4. **Verify what it found.** Inspect the leading generated C and identify the change that moved an instruction, register or delay slot. Express a useful change in readable project source and run the selected launcher’s `watch` on it. Compare against the same parent across the *whole* function, including regressions elsewhere, relocation operands and auxiliary data. A lower permuter score can be a lead even when the existing source still has more exact retail words. Protect evaluation order, volatile reads and writes, ABI and defined C behavior.
5. **Feed the result back.** Use a verified improvement as the next seed. If the best result ties or regresses, keep the old best, inspect the first unexplained difference and change the source or the search region for the next pass. Preserve a partial fix when it gives the worker a concrete lead on a parked function. Continue until every target is ready for the complete-wave handoff.

## Reuse a finding on another function

**Donor.** When an experiment changes the next decision another worker could make, put one compact entry in the existing private cursor or research observation. Keep a resolvable source pair and report. Include the symptom, what was already correct, the one C change, the actual local and whole-function effect, a case where it failed if known, the input set and a condition that makes the idea inapplicable. A partial fix can be worth sharing.

For the current wave, the same worker can carry a finding directly to the next target. When several workers participate, the Director shares read-only links to their lesson entries. The integrator publishes durable observations and the Director indexes them. [Research intake and publication](../WORKFLOW.md)

**Recipient.** When the current symptom changes, a batch stalls, or a parked target resumes, check relevant new entries and existing intake. With the selected launcher, use `intake <symbol> --inputs <manifest> --scratch-root <primary>` and, where supported by that release, `--symptom register-allocation` or `--cross-limit 3`. Check whether the donor’s preconditions hold. Apply the smallest analogous edit to your own source alongside your current control. Record the donor link and the measured recipient outcome in your own cursor. If a parked target belongs to the other worker, leave the lead for its owner; keep the one-current-target rule.

**Example entry:** “Display, decimal parser. Two registers are now correct, but initializing the flag earlier displaced a literal from a branch delay slot. One short-circuit test with a common assignment restored both positions; the frame and 611-word extent held. Look for duplicate flag-setting paths with the same evaluation order. An unresolved call operand is a different symptom.” [Donor source controls](../../build/matching/army-display/55B28-reconstruction.md)

## Complete-wave handoff

Keep successful sources, their guarded reports, and unresolved relocation or interface questions together. The integrator reconciles interfaces, checks sole ownership and linked bytes, and verifies the complete Rev 0 ROM at the wave boundary.
