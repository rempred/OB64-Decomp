## Outcome and finite scope

Integrate the identified library C through the existing production build, preserving
the exact US Rev 0 ROM and making the accepted source usable for later modifications.
Use the successful reference profiles to avoid rediscovering solved algorithms and
instruction schedules. Reference matches are inputs to integration, not acceptance.

[scope.json](scope.json) fixes the assigned membership by ROM entry, complete physical
owners, reference source, and research witness. It is a planning roster, not another
progress database. Current generated status and verification own acceptance counts.
The [expanded inventory](../../../build/director-resume-20261015/standard-library-inventory/report.md)
and its retained source/object/link evidence establish the starting point.

The core is all 210 not-yet-PURE_C C entries with exact reference evidence. The plan
also includes two explicitly **nonexact** completion companions in L7: `osInitialize`
at ROM `0x28450` and `_Printf` at `0x29FE0`. They keep the initialization/formatting
source families whole rather than hiding unfinished work behind matched helpers.
This makes a 212-entry C assignment. These entries are not necessarily
212 canonical targets; producers, logical bodies and physical owners differ.

Protect the six already accepted C entries that participate in these source families.
They may need to remain in a complete producer but receive no new progress credit.
Keep the 44 assembly entry spans in their existing assembly ownership. Exact stock
assembly is useful identification evidence; converting it to C is not this program.
The KMC arithmetic archive match remains assembly. Existing LHa acceptance, IPL3,
RSP microcode, unclassified candidates and unrelated programs are excluded.

The scope distinguishes 59,760 bytes of exact candidate function bodies from the
60,588-byte reference-text opportunity that includes native padding. The two L7
companions add 1,968 function-body bytes. Neither figure is an advance claim of
canonical matching-C bytes. Partial-owner bytes and padding never become functions.

### Reproduce the library profiles in production

Production currently takes one global compile-flag list from
`config/phase8/matching-c.json`. SDK witnesses commonly use O3, different character
signedness, SDK/F3DEX definitions and the compiler's `VR4300MUL` environment setting.
Changing the global O2 configuration would disturb existing accepted sources.

Propose the smallest finite **per-producer profile selection** needed by the retained
witnesses, with the unchanged legacy profile as the default. A group has one profile
for its complete producer. Do not add arbitrary command-line flag overrides, an
automatic compiler search, or a new toolchain. Use the pinned compiler, preprocessor
and GNU 2.6 executables. A profile identifies actual flags, preprocessing definitions,
include dependencies and relevant environment; it is not just an optimization label.

The effective profile must reach standalone and grouped compilation, supported private
checks, linked diff, source/object proof, cache identity, CURRENT fingerprint, strict
verification and fresh reproduction. Unknown profiles and stale/mismatched identities
must reject. Existing targets must retain their effective inputs and byte output.
Recipe names such as J/K are reproduction conditions, not proof of a unique SDK release.

Inspect the existing native-function group, auxiliary and retained-padding contracts
before proposing extensions. Reuse supported modes. Add only a demonstrated missing
capability, with a real failing library producer and an adversarial rejection case.
Do not build a general SDK importer or replace the current build/verification framework.

### Close owners, symbols and data before assigning complete waves

For each proposed wave, bind reference functions to current logical entries, complete
physical owners, native producer units, aliases, placement and source policy. Keep
multi-function units and local helpers together. Existing group support is broader
than the original version-1 documentation; inspect the current implementation rather
than assuming every multi-entry object needs new tooling.

Known issues to resolve from ROM/project evidence under the structural audit:

- Executable flags conflict with SDK instruction evidence at `0x1E7C8`, `0x1FBFC`,
  `0x1FC1C`, `0x24250` and `0x28FC0`. Check entries, callers and complete boundaries;
  do not flip flags solely because an external reference matches.
- `0x283C4` contains a 12-byte object-padding contribution within a larger data owner.
  Do not reclassify the whole data owner as code. Other partial padding at
  `0x2035C` and `0x2D7F0` stays separately accounted for.
- `osCreateThread` and `osGetThreadPri` share one 240-byte physical owner.
  `__createSpeedParam` has a 184-byte demonstrated body in a 192-byte owner.
  Close all remaining bytes; do not accept a sliced research object as a whole owner.
- Preserve actual weak/global aliases and caller interfaces. Byte-identical PI/SI
  templates and framebuffer accessors do not establish unique semantic names.

Native reference objects can define globals, writable data, BSS, readonly constants
and switch tables. The inventory proved text, not those data sections. Locate their
actual game bindings and ownership. Use existing retained data or explicit supported
producer/auxiliary contracts; introduce no duplicate storage, COMMON allocations,
speculative data placement or unverified copied tables. Shared headers must express
the observed 32-bit ABI, layouts and qualifiers and preserve existing consumers.

Research zero bindings for symbols used outside a compared slice and diagnostic
readonly-flag adjustments are not production permissions. Every accepted relocation
must resolve through actual canonical symbols/owners. A function-only witness needs
a reproducible complete C producer under the accepted contracts before integration.
Never copy its already-linked bytes into an output object.

Keep current physical boundaries where the existing representation can express the
producer faithfully. If a structural correction is necessary, make it explicit and
independently review it. The scope roster has no cross-wave physical-owner overlap,
but complete producer/data dependencies still need this admission check. Merge coupled
waves before dispatch if required; do not silently remove a difficult member later.

## Integration and acceptance loop

1. Reconcile the complete wave with current accepted inputs and F0's owner/profile
   decisions. Reproduce the chosen reference result, then use permitted source intake
   and real canonical declarations. Preserve the whole native producer context.
2. Run focused canonical linked diff and mechanical source policy while preparing each
   complete target/group. Check actual relocations, full body/owner coverage, native
   padding and any auxiliary contribution. Preserve provisional results and continue
   through every member. No full-ROM check after each function.
3. At complete-wave integration, the production writer drains only affected native
   checks, installs the whole candidate wave and checks changed shared consumers.
   Workers can continue private reasoning during that short drain.
4. Run **one final `node tools/verify.js`** for the combined inputs. The verifier builds
   CURRENT when needed; do not precede it with a redundant build. Confirm every new
   wave member is PURE_C and has sole C ownership, correct placement and actual
   relocations, exact target bytes, and the exact complete Rev 0 ROM. Retained hybrids
   elsewhere make global `--require-pure` inappropriate. Use the structural audit's
   integrated verifier instead when an actual structural delta requires that audit.
5. Record the accepted wave and minimal related changes on `main` under the activated
   commit policy. Reverify only if integration changes the verified inputs. Refresh
   affected candidate contexts, release drains immediately, and dispatch the next wave.

Do not relax equality, source policy or ownership for library code. Keep compiler
assembly untouched under the existing section/projection rules. No inline-assembly
shortcut, byte patch, relocation masking, fabricated padding or source exception can
turn a reference result into PURE_C acceptance. No blanket independent source review
or duplicate fresh-ROM build is added to ordinary waves.
