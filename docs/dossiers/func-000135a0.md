## Matching Lesson

The old compiler's choice of CPU registers depends on how the C variables are
written, even when two versions of the C do the same work.

The session spent substantial time trying to explain the compiler's register
choices in theory. Those explanations did not establish the answer. The useful
lesson comes from the versions that were actually compiled and compared.

The successful sequence was:

1. Writing the `+0x14` read and write before the `+0xA2` read and write fixed
   the two registers used at the loop head.
2. Writing both byte tests as `>= 0x80` produced the retail branch order,
   including the same delay-slot behavior. At that point the generated function
   had the right 49-instruction layout, but several registers still differed.
3. Earlier versions reused one cursor local for the possible byte reads.
   Giving all three reads separate cursor locals made the state pointer,
   constant, cursors, and byte value use the retail registers. Only the final
   two arithmetic instructions still differed.
4. Making `high_bits` a signed `s32`, then adding `2` to it in a separate
   statement before the final addition, fixed those last two instructions.

The exact integer widths also left visible clues in this function. Keeping the
countdown in a `u16` produced the retail 16-bit truncation before its comparison.
Keeping the parsed value in a `u8`, then comparing it as an unsigned value,
produced the retail byte mask before the comparison. These are useful clues when
a nearby candidate differs by a mask or truncation, but they are still
expression-specific observations rather than universal compiler rules.

The accepted version gives the three reads separate names:

```c
u8 *cursor_1;
u8 *cursor_2;
u8 *cursor_3;
```

The cursor split was the decisive change in the compiler's register choices,
but it did not by itself complete the match. The source-order, comparison, and
final arithmetic changes above were also required.

The useful rule is not “always use three cursor variables.” The useful rule is:

> When the generated code does the right work but uses the wrong registers,
> try giving values from separate reads or separate stages their own C
> variables. If retail clearly reuses one register, also try reusing a C
> variable. Compile after each focused change and let the byte diff decide.

Similarly, when the compiler groups commutative arithmetic differently from
retail, try ordinary temporaries and separate statements. In this match,
`high_bits = high_bits + 2;` followed by the final addition prevented the
compiler from choosing the other grouping.

These are useful things to try on a close match. They are not universal rules
for every function.

## What the Function Clearly Does

The code supports these plain structural descriptions:

| Offset | Observed job |
| --- | --- |
| `+0x38` | Points to the next unread byte. It advances after every byte read. |
| `+0xA2` | Counts down. When it reaches zero, the function reads a new value from the byte stream. |
| `+0xBC` | Stores the first byte, limited to its lower seven bits when the high bit is set. |
| `+0x14` | Increases by `0x100` on every loop pass. |
| `+0x0C` | Supplies the value that ends the loop when `+0x14` reaches it. |

When the countdown reaches zero, the function reads between one and three
bytes:

1. If the first byte is below `0x80`, it stores that byte at `+0xBC` and sets
   the new countdown to `1`.
2. If the first byte is at least `0x80`, it stores the lower seven bits at
   `+0xBC` and reads a second byte.
3. If the second byte is below `0x80`, the new countdown is that byte plus `2`.
4. If the second byte is at least `0x80`, the function reads a third byte. The
   new countdown is the lower seven bits of the second byte, shifted left by
   eight, plus the third byte, plus `2`.

This proves a compact one-, two-, or three-byte record shape and the jobs of the
fields listed above.

## What Remains Unknown

Matching bytes do not prove that this is the game's original C text. It proves
that this ordinary C produces the accepted retail machine code.

The code alone also does not prove the gameplay meaning of the stored value,
the countdown, or the time-like fields. The surrounding cutscene system makes
an animation or script role plausible, but names such as “choreography event,”
“director,” or “frame duration” need separate supporting evidence before they
become accepted semantic names.
