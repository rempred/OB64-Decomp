## Structural Reconstruction

The assembly supports this cautious description:

- each outer iteration consumes ten source bytes as five two-byte pairs;
- it writes one 25-byte destination record;
- destination bytes `0` and `1` receive an index-like byte and constant `1`;
- five first bytes are copied to destination offsets `2..6` when nonzero;
- five second bytes are copied to destination offsets `7..11` when the first
  byte is nonzero;
- five helper results are staged on the stack and passed to a five-argument
  helper whose byte result is stored at destination offset `24`;
- a first byte of zero stages a zero and skips the table lookup and first
  helper call;
- a first byte at least `100` subtracts three from a global byte, while the
  table lookup masks that value to index zero.

Names such as “character,” “formation,” or “movement” remain research
interpretations. This dossier does not promote them to accepted semantics.

## Placement Correction Before C Matching

The split's decoded PC comments place the function near `0x800DD3D8`, but those
comments are decode aids rather than the accepted overlay mapping. Overlay
descriptor 17 maps ROM `0x00069900` to VRAM `0x80197B70`. Therefore:

```text
0x80197B70 + (0x0006D7D8 - 0x00069900) = 0x8019BA48
```

The encoded `j 0x8019BB54` is consequently an internal jump to function offset
`+0x10C`, not an external tail call. It lands at the shared slot-advance tail.
The matching source shape is an ordinary `goto advance`; early experiments
with a `noreturn` callee were based on the stale decoded address and were
discarded.

This is the durable lesson:

> Resolve the accepted placement and subtract the function's accepted live
> entry before classifying an absolute jump as internal or external. Do this
> before inventing a callee prototype or unusual control flow.

The same care applied to the inner back-edge. Its exact target is the per-slot
load, not the destination-record header stores. The header stores therefore
belong to the outer loop and run once per record. Reading that target correctly
removed a large false mismatch cluster.

## Fixed-Layout Aggregate Experiment

The retail instructions directly establish these stack facts:

- frame size `0x58`;
- five staged bytes at `sp+0x18..sp+0x1C`;
- one pointer stored at `sp+0x24` and loaded once per outer iteration;
- that pointer is initialized to `sp+0x18`; and
- saved registers begin at `sp+0x30`.

They do not establish the names or purpose of the unused bytes between those
accesses. The first session pass incorrectly treated those gaps as evidence for
otherwise inaccessible local variables and tried oversized arrays and
`volatile` padding. Those forms could enlarge the frame, but they moved the
pointer spill and disturbed register allocation.

A single fixed-layout aggregate reproduced all observed offsets together:

```c
typedef struct Func0006D7D8Scratch {
    u8 movement_bytes[5];
    u8 unknown_05[7];
    u8 *movement_start;
    u8 unknown_10[8];
} Func0006D7D8Scratch;

Func0006D7D8Scratch scratch;
scratch.movement_start = scratch.movement_bytes;
```

With this target and compiler, the local aggregate began at `sp+0x18`, placed
the pointer field at `sp+0x24`, produced the `0x58` frame, and kept the five
byte loads at `sp+0x18..sp+0x1C`. This does not prove that the original source
used this exact struct. It proves that an ordinary aggregate is a plausible and
useful way to express a stack layout whose relative offsets are all observed.

The broader rule is:

> When several stack objects have a proven fixed relationship, try one local
> aggregate before adding dummy padding or attempting to steer independent
> local allocation. Keep unobserved bytes neutral.

## Other Reproduced Source-Shape Results

Several focused changes were useful and survived into the preserved candidate:

- An internal `goto` reproduced the zero-byte path's forward `j` and shared
  slot-advance tail.
- Bottom-tested `do` loops reproduced the inner and outer back-edges and their
  useful delay slots.
- Keeping the destination first-byte store as direct global indexing avoided a
  pointer-walk form that the optimizer hoisted and strength-reduced.
- This branchless source:

  ```c
  class_index = source_pair[0];
  class_index &= -(class_index < 100);
  ```

  produced the retail `sltiu`, negate, and `and` mask sequence.
- Multiplication by the 56-byte record stride produced the retail
  shift/subtract/shift sequence: multiply by eight, subtract the original
  index to form seven, then multiply by eight again.
- Moving only `index = 0` above the early-return guard changed prologue
  scheduling from the 42-difference aggregate candidate to the 31-difference
  `vT` candidate. It placed the zeroing between the retail save instructions
  without changing the loop body.

These are scoped observations for this target. They are experiments to try when
the same instruction clues appear, not general promises about KMC GCC.

Its section size was reported as 416 bytes because it contained twelve trailing

- five setup-register differences at `0x038..0x04C`;
- four destination-address ordering differences at `0x0B8..0x0C4`; and
- nine class-table address-scheduling differences at `0x0D8..0x0F8`.

The session's final report accidentally called the first group “ten relocation
pairs” and estimated about fifteen real differences. The raw list contains ten
words, not ten pairs. If all thirteen apparent relocation positions resolve as
expected, eighteen positional instruction differences remain. Because the
canonical linked diff was not run, even that relocation classification remains
an informed expectation rather than accepted proof.

## Experiments That Did Not Establish a Rule

The transcript contains many theories about GCC register preference and local
allocation. None produced a reliable allocator model. In particular:

- declaration-order and setup-order sweeps often canonicalized identically or
  changed unrelated allocation;
- unused ordinary locals were optimized away;
- `volatile` padding changed the frame but also changed stack placement and
  register allocation;
- an oversized staging array moved the pointer spill;
- duplicated inline mask expressions produced duplicated work and a much worse
  result;
- prescaling the class index, pointer-chain destination expressions, and
  per-slot destination temporaries all worsened the comparison;
- changing the function to return `u8` without producing a return value did not
  reserve `$v0`; and
- one-statement versus two-statement mask forms and swapped subscript operand
  order eventually canonicalized to the same 31-difference output.

Do not promote the session's changing explanations of allocator cost or
preference into compiler rules. The useful facts are the compiled outcomes
above.
