# Chunk 3 — RSP microcode bundle + text-VM tables + overlay code tail (`0x00031000..0x00041000`)

Source-ownership pass for the fourth 64 KiB chunk. **DATA-DOMINANT**, not a
function chunk: ~91% is data (a bundle of N64 RSP microcodes, zero-fill, the
text-VM jump table, glyph/rodata tables), and only the tail `0x3F1B0..0x41000` is
executable code (overlay-relocated). **67 tracked parts** under
`asm/original/rev0/lib/`: 23 code (`func_*`) + 44 data
(`rsp_ucode_*`/`zero_fill_*`/`table_*`/`data_*`). Byte-exact rebuild preserved
(code SHA `40D4E787…B409`, ROM SHA `571E8339…CC67A`).

This was handled as a classification pass (not a blind function split): every byte
in `0x31000..0x41000` is owned by an honestly-classified code or data part.

## Code/data oracle and the resolved BSS/overlay question

The earlier "`0x3F1B0` = RAM `0x800AEDB0` = BSS-clear start" contradiction is
**resolved**: above ROM `~0x2F000` the linear `RAM = ROM + 0x8006FC00` map is
unreliable (overlays). The parent overlay map (real RAM snapshots) shows the tail
functions are overlay-relocated — `0x3F1B0`→RAM `0x800E9C20` (just past BSS, not
into it) and `0x40E90`→RAM `0x8016AF90` (a second slot). So they are **real code**,
just not at their linear address; their RAM and any RAM-resolved globals/callees
are therefore unreliable, so all 22 are kept conservative `func_*`.

Three independent signals agree `0x31000..0x3F1B0` is **data, not code**:
1. Overlay map: **0 loaded functions** in that range across 21 snapshots.
2. `dump_function_context`: 0 detected functions (first is `0x3F1B0`).
3. Disasm scan: **0** `addiu $sp,-N` prologue + `jr $ra` signatures (34 `jr $ra`
   words are isolated data coincidences).

## What the data is (hard evidence)

- **RSP microcode bundle** (`~0x31000..0x3F1B0`): the standard N64 SDK graphics
  microcodes, proven by their name strings — `RSP Gfx ucode F3DEX / F3DEX.NoN /
  F3DEX.Rej / F3DLX.Rej / L3DEX / S2DEX / S2DEXD … fifo 2.08 … Yoshitaka Yasumoto
  1999 Nintendo`. Continues from chunk 2's `data_0002E450_rsp_ucode`. ~26 KB of
  ucode instruction/data + ~6 KB interleaved zero-fill.
- **text-VM jump table** (`table_text_vm_jump_table`, `0x387C0..0x3C100`, 14,656 B,
  306 pointer words): the `text_vm_jump_table` anchored at `0x39CB0` → RAM
  `0x800A98B0` (per parent `overlay-system.md`/`table_map.json`), plus the glyph
  charset string `:=;().,!?*-+/'"#$%&\[]|@{}<>^_~` and related tables.
- **zero-fill** blocks (uninitialized-data image, 6,208 B) and a few **mixed
  rodata/table** spans (`data_*`, "needs follow-up").

## Code tail (overlay-relocated; all `func_*`)

`0x3F1B0..0x40638` (group 1 → RAM `0x800E9C20+`, 19 functions incl. the frameless
leaf `func_0003fe68` the parent DB missed), a data gap `0x40638..0x40E90`
(`data_00040638`), then `0x40E90..0x41000` (group 2 → RAM `0x8016AF90+`).
`func_00040f88` `[0x40F88,0x40FF4)` is a COMPLETE leaf (returns at 0x40FEC). The
real straddler is `func_00040FF4` `[0x40FF4,0x41098)`: head
`func_00040ff4_chunk3head` `[0x40FF4,0x41000)` here, tail
`func_00040ff4_chunk4tail` `[0x41000,0x41098)` in chunk 4 (the parent DB
over-merged 0x40F88+0x40FF4 into one size=272 record; corrected 2026-06-21).
An adversarial review confirmed all 23 are real functions; structural roles noted
(jump-table state machines, table copy/init, scan/insert) but names stay `func_*`
because overlay RAM makes callee/global identity unverifiable.
