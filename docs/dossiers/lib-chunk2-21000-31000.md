# Chunk 2 — libultra / libc / runtime / gu library (`0x00021000..0x00031000`)

Source-layout split of the third 64 KiB code chunk (RAM `0x80090C00..0x800A0C00`,
simple mapping `RAM = ROM + 0x8006FC00`, verified linear across the whole chunk —
no overlay relocation here). **216 tracked files** under `asm/original/rev0/lib/`.
Byte-exact rebuild preserved (code SHA `40D4E787…B409`, ROM SHA `571E8339…CC67A`).

This chunk is overwhelmingly the **Nintendo N64 SDK (libultra) + libc + compiler
64-bit runtime + `gu` matrix library** statically linked into the game — the most
recognizable code seen so far. Names are exact SDK/libc symbols where the idiom is
unambiguous.

## Method

Same proven pipeline as chunk 1: `dump_function_context` (193 parent records) →
deterministic base partition (180 files) → 10-slice analyze→adversarial-review
swarm → integrate → split → byte-exact gate. The swarm un-merged hidden leaves,
recovered **undetected code** (the parent DB only detects standard `addiu $sp`
prologues, so it missed the libultra exception/thread/CP0 handlers that use
`k0`/`k1`, `mtc0`/`mfc0`, `jr $k0`), folded preamble-orphans, and split out
genuine **data** (RSP microcode + one small table). Net 193 parent records → 216
real files.

## Data regions (handled explicitly, NOT named as functions)

- `data_000283C4` `0x283C4..0x28430` (108 B) — small embedded table.
- `data_0002E450_rsp_ucode` `0x2E450..0x31000` (11,184 B) — **RSP microcode
  binary** (Reality Signal Processor vector instructions; from the host CPU's view
  this is data, not executable). It is the chunk's tail and **continues into
  chunk 3** (the `op_0x12`/COP2 words at `0x31000+` are the same ucode), so the
  parent DB's "function at `0x30008`" is a false positive inside ucode.

## Cross-chunk duplicate symbols

The game statically links libc/libultra into multiple translation units, so some
symbols recur across chunks. To keep asm labels unique, chunk-2 duplicates are
address-suffixed: `memcpy_00023884`, `memset_00023780`/`memset_0002cd70`,
`memcmp_0002cc90`, `strcpy_0002c950`, `strcmp_0002c9e0`, `strcat_0002ca20`,
`memmove_0002cc00`, `list_insert_head_000241f8`, `os_virtual_to_physical_000254e0`.
These are genuine separate copies, not mis-identifications.

## Boundaries (verified from disasm)

- Straddler tail `func_00020d40_tail` `[0x21000,0x210C0)` — continuation of the
  chunk-1 float routine `func_00020d40`, epilogue `jr $ra` at `0x210B8`.
- Undetected-code recovery: the libultra exception/thread/CP0 block was invisible

## Caveats / next frontier

- Medium/low-confidence names are hypotheses; `func_*` are address labels.
- **Next frontier `0x00031000` (chunk 3) is DATA-DOMINANT, not a function chunk.**
  `0x31000..~0x3F1B0` is the RSP-ucode continuation + zero-fill blocks (e.g.
  `0x34000`) + small-integer data tables (e.g. `0x3A000`: 5000/4000); the parent DB
  detects only ~21 functions, all at `0x3F1B0..0x41098` (which spill into chunk 4).
  Note `0x3F1B0` maps to RAM `0x800AEDB0` — the **BSS-clear start** from the boot
  entry — so the code/data/overlay status there is an OPEN QUESTION (functions at
  the BSS base would be zeroed at boot under the linear map; suspect overlay
  relocation or a rodata/initialized-data section). Chunk 3 needs a
  data-classification pass (data/rodata/ucode files + the tail functions), not the
  function-naming swarm. Resolve the `0x3F1B0` RAM/BSS contradiction before naming
  those tail functions.
