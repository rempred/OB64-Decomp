# How Ogre Battle 64 matching actually works

The strongest reason to decompile a function here is a change the editor can make better once the code is understood. In November, two new body/equipment matches completed six functions that contained ten editor patches. The native editor then expressed those changes in C and tested old exports. This is a practical target-selection criterion. The matching work itself benefits from changing how the worker chooses its next experiment. The evidence supports keeping the current compiler, clean-room boundary, sole production writer and complete-wave ROM verification. [Family census](../Plans/body-equipment-program.md) · [Editor adoption](../../../docs/Plans/task-logs/body-equipment-c-migration-20261109.md)

## From an assembly routine to an accepted change

A worker starts with the complete assembly owner, its calls and any data it owns. It reconstructs a candidate in a private workspace, often using m2c to start. The pinned KMC compiler shows how the reconstruction actually translates. The worker compares the emitted instructions, register use, branches and relocations. The integrator reconciles shared declarations, then verifies the complete wave against the original ROM. A source match answers whether that C produces the accepted bytes. Gameplay interpretation and editor usefulness get their own evidence. [Workflow](../WORKFLOW.md) · [Source policy](../SOURCE_POLICY.md)

### What the experiments cost

The following census reads every numbered direct report in the two retained November continuation series. It groups successful objects by executable section bytes and relocation identity, retaining the original relocation order and checking the declared relocations against the object. Comparisons stay within their target, selected input set and source class. A formatting confirmation and a failed hypothesis can both repeat earlier machine output for good reasons.

Each series also had one failed command. Including those failures, the reported process times were 547.2 and 160.0 seconds. The available compiler and assembler measurements together account for about 11.5 and 3.9 seconds respectively. These are child-process measurements. They exclude the initial workers' other attempts, work between commands, discussions and provider waits. They cannot establish the duration of a complete solve or a speedup. One source of confusion was the comparison itself. The final private symbolic reports still showed 20 and 39 differing instructions, respectively, in the two functions with 20 and 39 relocations. Both reports already set `rawObjectRelocationMaskedExact` to true. The workers also used local comparison scripts to mask relocation fields and account for internal jumps. The accepted map places B01 at runtime 0x8023C0B0 and B02 at runtime 0x8023B500, the bases those scripts use. Canonical linked verification later established exactness. ## What to borrow from human matchers

Human practice varies. Burk and colleagues observed human teams writing and compiling source against binary challenges. Their interface supported setting operand differences aside while reconstructing control flow, then returning to fine differences. The study concerned challenge programs across languages. It gives us a workflow to test on this game; it supplies no estimate of how much time an OB64 worker should take. [Decomperson, USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/burk)

In a closer comparison, Snowboard Kids 2 contributor Chris Lewis describes reading callers and thinking about the original data structure, using live assembly differences and applying agent suggestions. He reports that agents can identify patterns yet miss simple offsets. m2c supports rerunning inference with recovered types and prototypes. A human matcher can also specify a finite set of plausible source variants to the permuter. These practices transfer here with the project's own compiler and local, independently derived inputs. [Lewis's N64 account](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/) · [m2c context support](https://github.com/matt-kempster/m2c) · [decomp-permuter](https://github.com/simonlindholm/decomp-permuter)

## Could a new contributor recover the accepted source?

The working copy passed the current-source verifier even though a fresh Git checkout changed the bytes of 49 accepted C files. On the November 10 snapshot, the complete retained C and header input set contained 1,523 distinct paths. Git reconstructed 14 Windows-line-ending files as LF and also normalized 35 files with mixed endings. Nine other files already had correct, explicit Windows-line-ending rules. Comparing the raw Git objects alone would have incorrectly counted those nine as failures.

The correction preserves the 14 uniformly CRLF sources through ordinary checkout conversion and stores the 35 mixed-ending sources verbatim. No live compiler input changed. Two fresh repository indexes materialized the corrected files with `core.autocrlf` set to true and false respectively. Both reproduced all 1,523 SHA-256 values. The code diff with carriage returns ignored was empty. This checks the accepted source and header set; provisioning the private ROM and pinned host tools remains a separate step. [Checkout rules](../../.gitattributes)

After staging a completed, verified change to an authenticated source or its checkout rules, run `node tools/check_source_checkout.js` from the Decomp root using the pinned Node runtime. It materializes the retained source/header membership from the staged index and compares the resulting bytes to that acceptance record. A staged source edit awaiting a new verification naturally differs from the previous record. [Checkout checker](../../tools/check_source_checkout.js)

## Recommended operating model

To inspect current editor-priority annotations, use `node tools/match.js rank --priorities-only --lane leverage`. On this machine both unresolved actors appeared with seven and one static callers. The annotated view took 11.43 seconds; full ranking with a new isolated history database took 303.43 seconds. Full ranking includes candidate history and family evidence. An empty history, machine load and model size affect these times. [Benchmark and command coverage](matching-retrieval-replay-20261117.md)

1. **Begin with the editor question and the consumer.** Identify the actual game path, the complete owning routine and the editor workaround it might remove. Confirm callers, arguments, return width and data ownership before spending time on registers. Pick the smallest experiment that could disprove the proposed relationship.
2. **Choose the experiment from the difference.** A missing block points first to control flow or input meaning. Extra extension instructions at a call point to an interface check. Correct operations in the wrong order point to side effects, scheduling or liveness. A suffix outside the understood body points to placement or ownership evidence. These are working hypotheses; a compiler dump or source-pair control can disprove one.
3. **Give agents the mechanical bookkeeping.** Let tools compare bytes, relocation targets and prior emitted states. Group equivalent results and preserve intentional controls. Break a plateau with a different explanation and a test that distinguishes it from the incumbent one. Score-only iteration hid both November solutions. A private normalized comparison is a diagnostic before the linked check.
4. **Use a second perspective when it changes an experiment.** Send the paired consultant the smallest conflicting pair, what each candidate gets right, and the prediction that would separate two explanations. Save the answer alongside the observed result in the existing cursor. An assertion that a source form is impossible deserves a counterexample attempt. For service or quota failure, preserve the best candidate and dependency, notify the Director, and let the authorized owner resume or reassign it once. Retries that make no new request or experiment add little.
5. **Qualify changes in search or staffing before making them defaults.** On the next already-authorized comparable waves, record the initial mismatch before looking at a donor. Compare compact retrieval with the existing opt-in detail view. Record if the first suggested experiment changed emitted code in the predicted direction, time to the next discriminating result, total elapsed time, and eventual linked acceptance. Group observations by mismatch type and function size; report missing intervals and abandoned attempts. Test a constrained permuter on near-matches with known semantics and a small hypothesis space only after measuring a manual baseline. Retire a proposed change when it costs time without informing a decision. The retrospective queries yielded zero family suggestions in three cases. A later suggestion in the detailed view was plausible for one case. Prospective benefit remains unmeasured. [Retrospective replay](matching-retrieval-replay-20261117.md)

For wall-clock and storage measurements, use existing command profiles and recorded activity intervals with [wave accounting](../../tools/wave-accounting.js). A manifest names the wave, a time window with offsets, and whichever worker IDs, profiles, direct reports and exact scratch roots are available. Use the `--help` example field names. Run `node tools/wave-accounting.js --manifest <absolute-json-path>`. It reports overlapping and uncovered intervals. Missing timing stays unknown. A measurement of 222 B01 run directories found 26,935,624 bytes with insufficient retention metadata to classify their contents. Preserve those directories. November's separate maintenance already identified 19.6 GB of old metadata-test fixtures and moved them to Recycling. Reclamation is a separate owner decision. [Maintenance record](../audit/2026-11-10-splat-and-repository-cleanup.md)

The proposed change is to the experiment loop. The current release boundary already accepts complete-wave C, verifies sole object ownership and restores the exact retail ROM. The 36-target P02 wave spent about ten minutes on fresh normal acceptance. Evidence for the next investment is stronger around choosing experiments, interpreting their outputs and connecting a match to an editor change. [P02 acceptance timings](../audit/2026-10-29-attack-p02-integration.md)

The tooling run also exposed two test fixtures that had fallen behind C01. One omitted the four original assembly bytes following the accepted 1,004-byte C body on row 1831. The other omitted the physical head name from a synthetic multi-owner target after the implementation began checking its authority. Both were repaired against independent evidence and passed their focused suites. This is a reason to run the existing tooling tests when ownership machinery changes.
